# File sending — 0.4.0

The shop receiver remains independent of an explicit outgoing selection. A device-card click creates one immutable file-metadata snapshot and starts one outgoing batch. Drag/drop and clipboard actions only add selection. Classic Bluetooth uses Windows pairing, RFCOMM Object Push service discovery and a streamed OBEX client. CONNECT negotiation, optional Connection-ID headers, packet bounds and final PUT acknowledgements determine success. Errors, changed source metadata, refused offers and cancellation do not report Sent.

Quick Share uses the existing GPL encrypted protocol engine in a separate owned native process. A bounded JSON request file selects sources, destination and printable four-byte endpoint ID. The Windows app owns device discovery, GATT and Wi-Fi APIs; the native process owns UKey2, encryption, sharing consent, payload IDs and remote completion. Stdout is an internal JSON channel; Wi-Fi passwords never go to the activity log. Native command reading uses a detached standard thread so idle stdin cannot hold process exit after completion or failure. Cancellation kills only the owned sender process and disposes its transport.

mDNS browse only lists resolved same-subnet non-self addresses. Classic Windows discovery identifies paired entries honestly. BLE discovery parses public Nearby full advertisements or reads the FEF3 advertisement slot with bounded concurrency/deadlines. BLE endpoint and LAN service identities are kept separate; matching names are not merged because different customers can use the same phone name. Private/contact-only BLE advertisements are not exposed.

Compatible FEF3 GATT transports use a private loopback bridge and client-side weave negotiation/counters. Notifications are bounded and writes/ACKs serialize. Loopback EOF during a Wi-Fi upgrade does not cancel the encrypted sender. BLE connection failures become transfer failures; unsupported GATT profiles explain that a shared local Wi-Fi route is needed. Windows L2CAP CoC sending is not implemented.

The peer can offer a LAN endpoint, host a Wi-Fi Direct/hotspot network, or request a dynamic hosting-role switch. Windows joins a phone network manually and attempts to reconnect the prior saved network after completion/cancellation. Alternatively it starts a temporary local Wi-Fi Direct group through the existing offline hotspot controller. No code enables Internet Sharing/NAT. Active incoming transfers block the start of a Wi-Fi change; a later receive can still race with radio reconfiguration and needs hardware qualification. Host and join lifetimes end with the outgoing batch. Permissions/firewall/radio limits are surfaced. Above 1 MB, failed Wi-Fi upgrade produces a clean failure instead of attempting an unreliable large BLE-only payload.

Folders become cancellable ZIP snapshots preserving subdirectories and empty folders. Links/junctions and excessive entry counts are rejected. Text becomes UTF-8 and clipboard images PNG at their original dimensions. Temp selection files live in owned GUID subdirectories outside the receive destination. Removal/exit cleanup cannot delete source files. Outgoing source size/timestamp changes are rejected before and after transmission; edits preserving both attributes are not independently detected. Original files are never moved. The payload transfer remains byte-preserving; no image resizing or photo compression is applied.

Validation includes actual OBEX sender/receiver duplex TCP streams, refusal, Connection-ID/255-byte packet negotiation, cancellation, source mutation, malformed replies, weave client/server counter wrap, advertisements, native P256 integer decoding, and packaged sender/receiver encrypted loopback using file/folder/text/image selections. These are software checks. Actual Android/Samsung outgoing transfer, L2CAP compatibility, Wi-Fi role switches, OS pairing prompts and physical radio throughput are not proven by them.
